# 0008 — The nous lockfile: format and locked resolution

**Status:** Accepted (1.7.2, maintainer decisions on format, I/O, drift and apt)

## Context

nous resolves deterministically: the same inputs give the same graph. But the
inputs change. Marketplace packages are published, recipes are bumped and apt
takes security updates, so nothing pins a resolution across time or machines.
The ark v2 sovereignty path names a lockfile as nous's half of milestone M2
(agnosticos `docs/development/planning/ark-v2-sovereignty-path.md`). Its
acceptance criterion is ark installing "from the local store with a committed
lock".

What nous cannot do changes the design. nous has **one candidate per name**:
the registry holds installed versions, apt is queried with
`--no-all-versions`, and a recipe has one version. So it cannot "prefer the
locked version" when another is available, as Cargo or pub do. A lock can only
**pin and verify**: record the graph, then refuse a resolution that differs
from it. Version selection is gated on a multi-version source (roadmap).

## Decision

The maintainer chose four points: the format, who does the I/O, what happens
on drift, and how apt is treated. The rest are defaults, recorded here.

- **Format: CYML, in the Cargo.lock style.** It is the same TOML-like family
  as `cyrius.cyml` and zugot recipes, parsed by the bayan-toml profile nous
  already depends on, and it diffs well in review:

      # nous lockfile: generated by nous_lock_to_str; do not edit by hand.
      version = 1
      roots = ["acme/scanner", "curl"]

      [[package]]
      name = "curl"
      version = "8.19.0"
      source = "community"
      dependencies = ["glibc", "openssl"]

  - The output is byte-stable for the same graph. Packages, roots and
    dependencies are in byte order, and there is no timestamp or nous
    version.
  - A package's `dependencies` are its edges to other locked packages. A
    name apt could not show (a virtual package; see `nous_pl_unresolved`) is
    apt's to resolve and is not locked.
  - A value must be printable ASCII without `"` or `\`. nous's CYML reader
    does not decode escapes, so instead of an escape scheme, a plan holding
    any other byte is refused when it is locked (`NOUS_ERR_INVALID_LOCKFILE`).
    Real names and versions never contain one.
  - A JSON encoding (`nous_lock_to_json` / `nous_lock_from_json`) exists too,
    because CLAUDE.md requires JSON both ways for every public type. The
    file format is the CYML.
- **I/O: text in, text out.** `nous_lock_to_str` and `nous_lock_parse` work
  on Strs. The consumer (ark) picks the path, writes atomically and commits.
  nous still writes no files.
- **Drift is a strict error.** `nous_resolve_locked(r, lock)` resolves the
  lock's roots and compares the result with the lock. The comparison catches
  a changed version, a changed source, a changed dependency list, and a
  package added or missing. Any of these is
  `Err(NOUS_ERR_LOCK_MISMATCH)`, naming the differences and saying to
  regenerate the lock to accept them (like `cargo --locked` and `npm ci`).
  `nous_lock_diff(old, new)` reports the same differences without failing,
  for "what would change".
  - A source change is drift. A name that resolves from a different source
    than the lock says is refused, which is dependency confusion across
    time.
- **apt packages are locked and enforced** like every other node. After an
  apt upgrade, locked mode reports the drift, and regenerating accepts it. On
  agnos there is no apt, so this only applies to the Debian compat mode.
- **Parsing is strict about what it needs and lenient about what it does not
  know.**
  - Refused: an unknown `version` (only 1 exists); a missing or duplicate
    package name; a missing version, source or dependency list; an unknown
    source; a dependency or root that is not a locked package.
  - Unknown keys are ignored, so 1.7.3 can add an artifact checksum without
    breaking 1.7.2 readers.
  - Input in any order is accepted and normalized to byte order.
- **Locked resolution uses the recipe DB when the resolver has one attached**
  (`resolver_with_recipes`), as `resolver_resolve_all_with_recipes` does.

## Consequences

- **A committed lock makes resolution reproducible or refused, never
  silently different.** The error says what moved.
- **Regenerating is the consumer's act.** It resolves, calls
  `nous_lock_from_plan` and writes the text. nous has no "update the lock"
  mode, because with one candidate per name, an update is just a new
  resolution.
- **On Debian, a lock goes stale after apt security updates** (by decision).
  The drift report names each package and its versions.
- **Two error kinds are added:** `NOUS_ERR_INVALID_LOCKFILE` (9) and
  `NOUS_ERR_LOCK_MISMATCH` (10). A consumer matching kinds exhaustively must
  handle them.
- **1.7.3 adds integrity:** an artifact hash per node, which locked mode then
  checks. The format reserves room for it through the unknown-key rule.
